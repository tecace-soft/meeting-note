# U1/U9 자동 요약, 자동 화자 제안, 이름 반영 요약 갱신 설계 메모 (웹)

근거는 REFACTOR_PLAN.md 개정 3의 5절 U1, U3, U4, U5, U9, U1/U2 진입 경로 표, U9 완료 기준, 6절 A1과 A4, 4.2 S11이다.
결정은 DEC-0024(Andrew, 2026-10-28)에 기록한다.
이 메모는 웹 첫 조각만 다룬다.
모바일(U2와 모바일 U9)은 별도 PR이다.

## 1. 범위와 결정 요약

1. 녹음을 멈추면 업로드와 요약이 자동으로 시작한다(U1).
   프롬프트, 추가 지시, 첨부는 접힌 "옵션"으로 옮기고 기본값을 쓴다(U3, U4, U5).
2. 노트가 생기면 화자 이름 제안이 자동으로 계산되어 보인다(U9).
   제안은 미리 채움일 뿐이고 적용은 사용자가 누른다.
   이름은 적용 전에도 적용 후에도 바꿀 수 있다.
3. 주요 화자가 모두 실제 이름을 가지면 짧은 대기(debounce) 뒤 요약을 한 번 다시 만든다.
   이후 이름을 바꾸면 다시 대기 뒤 갱신한다.
   "이름 반영해 요약 업데이트" 버튼은 항상 보인다.
4. 사용자가 요약을 직접 고쳤으면 자동으로 덮어쓰지 않고 "새 요약으로 바꿀까요?" 알림을 보인다.
5. 제안된 이름은 사용자가 확인하기 전에는 요약에 들어가지 않는다.

플래그는 두지 않는다.
계획(5절)은 U1과 U9를 기본 동작으로 승인했고 플래그를 요구하지 않는다.

## 2. U1 흐름 (녹음 후 자동 요약)

```
녹음 중지(이 화면의 중지 버튼, 떠 있는 녹음 위젯의 중지, 2시간 자동 중지)
  -> 녹음 길이 < MIN_AUTO_SUMMARY_SECONDS(5초)?
       예 -> 완료 패널(재생, 다운로드, 버리기, "요약") + "짧은 녹음이라 자동으로 시작하지 않았습니다"
       아니오 -> 유예 카드 "N초 뒤 요약을 시작합니다 [취소]" (AUTO_SUBMIT_GRACE_SECONDS = 5초)
                 취소 -> 완료 패널로 돌아감(아무것도 업로드하거나 제출하지 않음)
                 유예 종료 -> 업로드 -> 업로드 완료 -> S11 제출 기록 저장 -> POST /summarize-audio/jobs -> 기존 폴링
```

```
파일 업로드 선택
  -> 업로드 시작(현행) + 동시에 유예 카드
       취소 -> 업로드는 끝까지 진행하고 파일은 남는다; 요약은 제출하지 않는다("요약" 버튼으로 수동 시작)
       유예 종료 + 업로드 완료 -> S11 제출 기록 -> POST
최근 녹음 선택
  -> 이 녹음을 참조하는 노트가 있는지 확인(fetchReferencingNotes, 소유자 범위)
       있음 -> 자동 제출하지 않고 "이미 이 녹음으로 만든 노트가 있습니다 [노트 열기]" + 수동 "요약" 버튼
       확인 실패 -> 자동 제출하지 않음(fail-closed), 수동 "요약" 버튼
       없음 -> 유예 카드 -> 유예 종료 -> S11 제출 기록 -> POST
```

진입 경로별 동작(계획의 U1/U2 표를 그대로 따른다):

| 진입 경로 | 자동 시작 | 구현 |
| --- | --- | --- |
| 이 화면에서 녹음 중지 | 예(짧은 녹음 제외, 유예 후) | 중지 버튼이 의도를 표시하고 녹음 결과가 생기면 유예 시작 |
| 떠 있는 위젯에서 중지 | 예 | 위젯이 `navigate(..., { state: { autoSummarize: true } })`로 이동, 화면은 state를 한 번 쓰고 지운다 |
| 2시간 자동 중지 | 예 | 이 화면에 있으면 `recordingAutoStopped`로 감지; 다른 화면이면 위젯의 "녹음 확인"이 같은 state로 이동 |
| 중단된 녹음 복구본 | 아니오 | 복구 후 완료 패널의 "요약" 버튼 |
| 녹음 중 이동 확인의 "중지하고 이동" | 아니오 | 의도 표시가 없으므로 돌아왔을 때 완료 패널에 남음 |
| 파일 업로드 | 예(유예 후) | 위 흐름 |
| 최근 녹음 선택 | 예, 단 참조 노트가 없을 때만 | 위 흐름 |

입력 snapshot: 제출 시점의 프롬프트, 추가 지시, 첨부를 요청 본문에 고정한다(현행 handleSummarize와 같음).
옵션은 녹음 전과 녹음 중에도 접힌 "옵션"에서 바꿀 수 있다.
요약 뒤 노트에 추가하는 첨부는 요약 입력에 들어가지 않는다(U5, 문구 유지).

취소 경계: 유예 중 취소는 서버에 아무것도 보내지 않는다는 뜻이다.
POST가 나간 뒤에는 서버 취소 API가 없으므로 취소 버튼을 보이지 않는다.

## 3. U9 흐름 (자동 화자 제안)

```
job 완료 -> 요약 화면 표시
  -> 결과 위쪽에 "누가 말했나요" 카드(TranscriptDiarizedEditor suggestionPanel="only", autoSuggest)
  -> 익명 라벨이 있고 이 노트를 이번 세션에 자동 계산한 적이 없으면 identify-speakers 1회 호출
  -> 제안 표시: "Speaker A -> 이름 (85%) [적용]"
  -> 적용 = 기존 handleAcceptSuggestion(저장, 피드백 로그, 프로필 누적, insight 갱신; 공유하지 않음)
  -> 이름 수정은 전사 탭의 화자 메뉴(현행), 카드에 "전사에서 화자 고치기" 링크
```

- 제안 상태는 모듈 단위 저장소(`src/lib/speakers/suggestionStore.ts`)에 `noteId + 전사 revision` 키로 둔다.
  revision은 각 구간의 speakerKey와 원문 텍스트의 해시다.
  이름 바꾸기는 speakerKey를 바꾸지 않으므로 revision이 그대로이고, 텍스트 수정은 revision을 바꿔 이전 제안을 버린다(U9 완료 기준).
- 같은 키의 요청은 동시에 하나만 진행한다.
  탭 전환이나 재방문으로 편집기가 다시 마운트돼도 다시 호출하지 않는다.
- 자동 호출은 노트당 세션에서 한 번이다.
  revision이 바뀐 뒤에는 사용자가 "다시 제안"을 눌러야 한다.
- 화면에 보이는 제안은 지금 전사에서 아직 익명인 라벨의 제안뿐이다.
  그래서 사용자가 먼저 이름을 고친 라벨에 늦게 도착한 제안은 보이지 않고 아무것도 덮지 않는다.
- 저장소는 최대 50개 키를 넣은 순서대로 버린다.
  identify-speakers 요청은 60초 timeout을 둔다.
- SummaryHistory는 autoSuggest를 켜지 않는다(이 PR은 새 노트 화면만).
  같은 저장소를 쓰므로 그 화면에서 누른 제안도 다시 열 때 남는다.

## 4. 이름 반영 요약 갱신

### 4.1 주요 화자

- 화자 단위는 speakerKey(없으면 표시 이름)다.
- 발화 시간 = 구간의 `end - start`(초) 합계.
  모든 구간에 유효한 시간이 없으면 원문 글자 수로 대신한다.
- 주요 화자 = 발화 시간이 전체 발화 시간의 `MAIN_SPEAKER_MIN_SHARE`(0.10) 이상인 화자.
  값은 `src/lib/speakers/mainSpeakers.ts`의 상수 하나이며 실제 데이터로 나중에 조정한다.
- 화자가 "이름 있음"이려면 그 화자의 모든 구간 라벨이 익명 라벨(isAnonymousSpeakerLabel: "Speaker A", "Speaker 1", "Unknown Speaker" 등)이 아니어야 한다.
- 이름 서명(naming signature) = 주요 화자가 모두 이름 있음일 때 `speakerKey=이름` 목록(모든 화자, 정렬); 아니면 null.
  부수 화자의 이름 변경도 서명을 바꾸므로 갱신을 부르지만, 부수 화자가 익명이어도 서명은 null이 되지 않는다(갱신을 막지 않음).

### 4.2 트리거, debounce, 중복 제거

```
전사 변경 -> 서명 계산
  서명 == null                         -> 아무것도 안 함
  서명 == 현재 요약의 기준 서명          -> 아무것도 안 함(같은 이름으로 다시 만들지 않음)
  서명 == 마지막 시도 서명               -> 아무것도 안 함(실패 반복 방지)
  진행 중인 재생성 있음                  -> 끝난 뒤 다시 평가
  자동 횟수 상한 도달                    -> "자동 갱신 멈춤" 안내, 수동 버튼만
  그 밖                                -> NAME_REFRESH_DEBOUNCE_MS(4초) 타이머; 서명이 바뀌면 타이머 재시작
타이머 만료 -> 재생성 1회(현재 전사, persist:false) -> 4.3 적용 규칙
```

- 기준 서명은 처음에 job 결과 전사의 서명이다(보통 null; 서버의 단일 화자 자동 명명은 job 완료 뒤 DB에만 쓰이고 이 화면 상태에는 오지 않는다).
  재생성이 적용되거나 알림을 닫으면 그 요청의 서명이 기준이 된다.
- 노트당 진행 중 재생성은 최대 1개다(자동과 수동이 같은 실행기를 쓰고, 진행 중에는 수동 버튼이 비활성).
- 자동 재생성은 노트당 화면 세션에서 `MAX_AUTO_NAME_REFRESHES_PER_NOTE`(3)회까지다.
  수동 버튼과 "다시 시도"는 사용자가 누를 때마다 실행되며 상한에 세지 않는다.
- 언마운트, 노트 변경(버리기, 새 요약)에서는 타이머를 지우고 진행 중 요청을 abort한다.
  persist:false라 abort된 요청은 아무것도 저장하지 않는다.
- 재생성 요청은 120초 timeout을 둔다.

### 4.3 수동 편집 판별과 적용 규칙

regenerate 라우트는 지금 `summary_edit`에 결과를 쓴다(routes/regenerateSummary.ts 125-128행).
그래서 `summary_edit`가 있다는 사실만으로는 사람이 고친 것인지 재생성 결과인지 알 수 없다.

정의: 이 화면이 아는 "생성된 텍스트" 집합 = job 결과의 요약과 그 번역들, 그리고 이 화면에서 적용한 재생성 결과.
요약이 "직접 수정됨"이면 아래 중 하나다.

- 지금 요약 편집 중이다(편집창이 열려 있다).
- 화면의 요약 텍스트가 생성된 텍스트 집합에 없다(이 화면에서 고쳐 저장했다).
- 서버의 `summary_edit`가 null이 아니고 생성된 텍스트 집합에 없다(다른 탭이나 기기에서 고쳤다); 읽기에 실패하면 직접 수정됨으로 본다(덮어쓰지 않는 쪽으로 실패).

비교는 앞뒤 공백을 뺀 문자열로 한다.
새 열이나 migration은 필요 없고 기존 행과 호환된다.

적용 규칙:

- 자동 갱신, 수정 없음 -> 소유자 범위 쓰기(`patchOwnedNoteReturningId`)로 `summary_edit` 저장 후 화면 교체.
- 자동 갱신, 직접 수정됨 -> 저장하지 않고 비차단 알림 "화자 이름을 반영한 새 요약이 준비됐습니다. 바꿀까요? [바꾸기] [닫기]".
  바꾸기 = 위와 같은 저장 후 교체, 닫기 = 버림(그 서명을 기준으로 삼아 같은 이름으로 다시 묻지 않음).
- 수동 버튼("이름 반영해 요약 업데이트") -> 사용자가 요청했으므로 바로 저장하고 교체한다(현재 Regenerate 버튼과 같은 의미).
- 실패(네트워크, 서버, 저장 0행) -> 이전 요약을 그대로 두고 오류와 "다시 시도"를 보인다.
  자동으로 다시 시도하지 않는다.

재생성 결과는 원문 언어 요약 하나이므로 적용할 때 화면의 이전 요약 번역(summaryTranslations)은 지운다.

### 4.4 서버 변경

1. `POST /regenerate-summary`에 선택 필드 `persist`를 추가한다.
   `persist: false`면 `summary_edit`를 쓰지 않고 응답에 `persisted: false`를 넣는다.
   생략하거나 다른 값이면 지금처럼 저장하고 `persisted: true`를 넣는다(모바일, SummaryHistory 호환).
   메모리 fold는 기존처럼 응답 뒤 best-effort로 실행된다(이미 접힌 노트는 건너뜀).
2. 재생성 프롬프트: 전사에 실제 이름과 익명 라벨이 함께 있으면, 익명 라벨 목록을 주고 "이름이 지정되지 않은 다른 참석자"로 다루라는 규칙을 덧붙인다(이름을 추측하지 않음, 참석자 이름 목록에 넣지 않음).
   모두 이름이거나 모두 익명이면 프롬프트는 지금과 바이트 단위로 같다.
3. 모델은 기존 `REGENERATE_SUMMARY_MODEL`(lite)과 `STANDARD_FALLBACK_CHAIN`(lite)을 그대로 쓴다(DEC-0005).

배포 순서: 백엔드를 먼저 배포한다.
옛 백엔드는 `persist`를 무시하고 저장하므로, 그 사이에는 직접 수정한 요약이 자동 갱신으로 덮일 수 있다.

## 5. 비용 상한 (DEC-0005, S13 전)

## 7. 테스트

- 순수 로직: 주요 화자와 서명, 제출 기록, 제안 저장소, 재생성 요청(timeout, 오류).
- renderHook: 이름 반영 갱신(debounce, 중복 제거, 상한, 실패, 수동 편집 알림, abort), 유예 타이머.
- 마운트: TranscriptionSummary 자동 흐름(유예와 취소, 짧은 녹음, 복구본, 이름 지정 뒤 갱신과 알림).
- 서버 계약: `persist:false`는 note PATCH를 하지 않음, 기본은 저장, 익명 라벨 규칙의 유무.
