# F5: Context-based Speaker Identification — Design

Status: PLAN (approved decisions locked 2026-08-12).
Owner: Andrew Yoo.
Relates to: F1' (`user_memory`), F4 (`note_insight` / index), F8 (evaluation), the owner-attribution fix (`5926c00`).

## 1. Framing (correct the premise first)

The boss described the current system as voice-pattern matching ("목소리 녹음해서 디프런스 계산") that F5 should replace with context.
That premise is wrong about the code: **the system is already context/text-based, and no acoustic voice identity is persisted anywhere.**

Ground truth (verified 2026-08-12):
- AssemblyAI (`universal-3-pro`) emits per-file `Speaker A/B` labels; labels are scoped to one audio file and carry no cross-note meaning.
- No embedding / voiceprint / vector store for speakers exists (pgvector is deferred; the Gemini `DIARIZATION_PROMPT` "voice fingerprint" text is dead code).
- Real names are produced by TEXT means only: manual rename in the editor, or the `identify-speakers` edge function (a Gemini text-signal suggester), then written into `note.diarization`.

So F5 is not a voice→context switch.
F5 = **automate, enrich, and move earlier the context-based identification that already exists, and make it measurable.**

## 2. Current architecture (what exists today)

- Diarization: `workflow-server/src/index.ts:1322` mints `"Speaker A/B"` from AssemblyAI; stored into BOTH `note.transcription` (text, frozen) and `note.diarization` (jsonb segments).
- Naming (write path): `src/components/TranscriptDiarizedEditor.tsx` → `persistNoteDiarization` (`src/lib/transcriptSegments.ts:180`) overwrites speaker names **in `note.diarization` only**; `note.transcription` is never rewritten.
- Suggestion: `supabase/functions/identify-speakers/index.ts` (Gemini `2.5-flash-lite`) returns per-label `{name, speakerId, confidence, isSelf, rationale}` from a roster of saved `speaker` rows + their `profile` summaries + `selfName`. Suggestion-only; manual trigger; user must Apply.
- Speaker profiles: `speaker.profile` (text column, ontology JSON) generated by `supabase/functions/generate-profile`; used only at REGENERATE summarize time, not at ingest or diarization.
- Per-user memory: `user_memory` (`workflow-server/src/memory.ts`), narrative fold, keyed by the logged-in user.
- MCP read: `get_note_transcript` diarized reads `note.diarization` (named); plain reads `note.transcription` (generic).

### The root asymmetry (also the owner-gap root cause)

Names live in `note.diarization`, but insight/memory/summary extraction reads the frozen `note.transcription` ("Speaker A/B").
That is exactly why `note_insight.actions[].owner` was empty until `5926c00` (which threaded `speakerContext` as a hint).
F5 closes it at the source by making `note.diarization` the canonical speaker record and feeding named text into extraction.

## 3. Decisions locked (2026-08-12)

1. **Identity source = pure context.** Text/context only (identify-speakers + `user_memory` + `speaker.profile` + MS attendees). No acoustic voiceprint. Acoustic deferred to F5.4 backlog.
2. **Apply policy = hybrid.** Confidence ≥ threshold → auto-apply to diarization; below → pending suggestion, one-tap confirm in UI. Threshold tuned by F8.
3. **Re-extraction included.** Confirmed names flow into `note_insight` + `user_memory` + action `owner` (not summary/display only).

## 4. Design principle

Make `note.diarization` the canonical speaker source of truth.
Treat `note.transcription` as a derived cache.
Insight/memory extraction builds its transcript from the named `note.diarization` (or re-runs after naming), so real names reach the structured index and memory.

## 5. Phases

### F5.0 — Identity flows to insight/memory (closes the owner gap) [do first]

Problem: extraction reads frozen generic `note.transcription`; names only in `note.diarization`.

Work:
- Add a server helper that builds the extraction transcript from `note.diarization` (named), not the frozen `transcription` column.
- On speaker rename/confirm (existing `persistNoteDiarization` write path), trigger server **re-extraction**: re-run `extractInsight` + `foldNoteIntoMemory` with a `speakerContext` derived from the confirmed diarization names.
- Hardest sub-part: `foldNoteIntoMemory` is idempotent via `processed_note_ids`; a re-fold on rename must **supersede** the note's earlier (generic) memory contribution, not duplicate it. This needs per-note memory provenance (which items/ops came from this note) so a re-fold can replace them.
- De-risk option for alpha: re-extract `note_insight` only (deterministic, per-note, safe) and defer memory re-fold superseding to a later step.

Deliverable: renaming a speaker updates `note_insight.people` + `actions[].owner` + `user_memory`.
Measured by F8 owner-coverage on a named golden.

### F5.1 — Server-side auto-identification at ingest

- Move `identify-speakers` from manual-only to **auto-run server-side right after transcription** (parallel with the memory fold).
- Reuse the existing Gemini logic (port into `workflow-server` or call the edge function) with the user's saved-speaker roster.
- Write suggestions into diarization with per-label confidence.
- Hybrid apply: ≥ threshold (start ~0.8, F8-tuned) auto-applied; below → pending suggestion surfaced in UI for one-tap confirm.
- Self-detection: mark the note owner via the existing `isSelf` signal.

### F5.2 — Richer context for the identifier

Feed the identifier beyond the current roster+profile:
- `user_memory` (the logged-in user's collaborators / relationships).
- `speaker.profile` ontology fields: `active_projects`, `relationships`, `responsibilities`.
- MS attendees / `note.shared_users` / calendar (if available) as candidate priors.
- Topic/project overlap: which saved speakers associate with this meeting's topics, via `note_insight` people×topics history.

This is where "accuracy improves as memory accumulates" becomes real.

**F5.2a attempt — memory-dump context: FAILED, reverted 2026-08-12.**
Fed the owner's `user_memory` (collaborators/roles) into the identify prompt.
Measured on the F8 speaker golden (2-person Hansoo/Andrew meeting, no vocatives): precision **100% → 0%**, consistent across runs — the model stopped abstaining and confidently assigned BOTH speakers, but SWAPPED them (A→Andrew, B→Hansoo at 0.9).
Root cause: the memory context says "both these people exist and their roles" but gives no per-speaker disambiguation for *this* meeting; it just tempts the model to force-assign, and role-inference from content alone is unreliable (it flips A/B).
Lesson: recall must not be bought with precision — a wrong 0.9 auto-apply corrupts the diarization. A memory dump is the wrong signal.
**Better F5.2 signals (not yet built):** the meeting's actual MS attendee list mapped to speakers (needs a data-availability check), explicit vocative/self-intro cue extraction, and only then a memory tie-breaker — always keeping the conservative "abstain unless the transcript itself identifies the person" rule. On a no-cue 2-person meeting, safely lifting recall may simply not be possible; that is an acceptable conservative outcome.

### F5.3 — Cross-note accumulation loop + F8 evaluation

- On confirmed identification, update `speaker.profile` (existing `accumulateSpeakerProfile`) and record identification evidence (text signals: aliases, frequent co-participants, topic affinity) so future matches are stronger. Extend the `speaker.profile` ontology rather than adding a table.
- F8 "speaker-id accuracy" surface: golden notes with known speaker→name truth; measure P/R of auto-identification, AND whether accuracy rises as roster/memory grow (the time-lagged evaluation the boss explicitly asked for).

### F5.4 — Acoustic voice embeddings [DROPPED 2026-08-12 — compute cost]

Per-speaker voiceprint (store the user's voice, cross-check across notes to identify speakers).
**Dropped, not deferred (decision 2026-08-12): the compute cost is too high to justify.**
AssemblyAI returns no embeddings, so this would need a separate embedding model + vector store running over every recording.
Speaker identification stays permanently pure-context (text signals + memory + profiles).
Do not revisit unless the compute economics change materially.

## 6. Risks / trade-offs

- Wrong auto-applied name corrupts memory → mitigated by the confidence threshold + re-fold supersede + user correction re-triggering re-extraction.
- Re-fold idempotency/superseding (F5.0) is the highest-difficulty engineering piece; fallback is note_insight-only re-extraction for alpha.
- Added ingest latency: one identify-speakers Gemini call (~2s), run in parallel with summary — acceptable.
- Cold start: an empty roster yields low confidence → suggest-only; accumulation improves it. Honest limitation to state to the boss.

## 7. Sequence and first alpha

Recommended order: F5.0 → F5.1 → F5.2 → F5.3 → (F5.4 deferred).

Smallest shippable alpha (demonstrable to the boss):
- F5.0 (note_insight re-extraction on rename) + F5.1 (auto-identify at ingest, hybrid apply).
- Result: new notes get names auto-suggested; confirming a name updates the structured index + owner.

F8 discipline: build the speaker-id golden + metric together with F5.1, so accuracy is measured, not assumed.
